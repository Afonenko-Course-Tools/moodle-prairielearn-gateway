# Экзаменационный запуск: подтверждённый студент и адрес сети

Необязательный `examAudit` связывает подтверждённый LTI UID и подписанное имя
с адресом клиента, переданным доверенным reverse proxy. Это наблюдение сетевого
адреса, а не отпечаток физического ПК, учётная запись Windows или доказательство
присутствия. При NAT один адрес может относиться к нескольким устройствам;
смена DHCP, прокси или адреса одного устройства может дать несколько адресов.
Диапазон `10.0.0.0/8` описывает разрешённую сеть, но сам по себе не определяет
конкретный учебный класс.

Функция выключена при отсутствии `examAudit`. Обычные курсы, LTI identity,
одноразовый handoff и штатные PL cookies сохраняют прежний договор.

## Серверная конфигурация

В закрытом runtime JSON добавьте к выбранному курсу:

```json
{
  "examAudit": {
    "examId": "synthetic-exam-2026-11-17",
    "activities": ["exam"],
    "database": "/absolute/private/exam-audit.sqlite",
    "proxyTokenFile": "/absolute/private/exam-proxy-token",
    "classroomCidrs": ["10.0.0.0/8"],
    "restrictLaunchToClassroom": false
  }
}
```

`exam` здесь — пример существующего ключа `registration.activities`.
Список должен быть непустым, без повторов и целиком входить в зарегистрированные
activity курса. Он выбирается оператором, не браузерным параметром или именем
ресурса. `examId` тоже задаётся сервером; меняйте его для следующего экзамена,
иначе прежние события будут участвовать в сравнении.

`classroomCidrs` содержит непустой список корректных CIDR с сетевым адресом
без host bits. `10.0.0.0/8` включает `10.0.0.0`–`10.255.255.255`.
IPv4-mapped IPv6 автоматически в IPv4 не преобразуется: `::ffff:10.1.2.3`
не попадает в IPv4 `/8`. Для IPv6 задайте отдельную сеть явно.

`database` — отдельная новая SQLite DB каждого курса. Существующая auth DB
по-прежнему содержит ровно две auth таблицы; аудит её схему не меняет.
Пути аудита не могут совпадать с auth DB, DB других курсов, service token или
CA, включая SQLite `-wal`, `-shm`, `-journal` и auth `.startup-lock`.
Учитываются физические пути и существующие hard links. Runtime пути и секреты
должны находиться вне репозитория; `tools/run-gateway.py` проверяет это для
DB и token файлов. Выберите закрытый родительский каталог, принадлежащий
оператору сервиса. Audit DB получает права `0600`.

Proxy token — отдельный обычный файл с правами `0600`, не менее 32 печатных
ASCII символов. Gateway читает его при запуске, сравнивает в постоянном времени
и не выдаёт браузеру. Для замены token требуется согласованно обновить Gateway
и Nginx. Ошибка чтения или открытые права дают degraded и неизвестный адрес,
а не доверие к публичным заголовкам.

## Доверенная цепочка источника

Gateway принимает ровно по одному значению двух private headers:

- `X-Exam-Proxy-Token` — секрет доверенного reverse proxy;
- `X-Exam-Client-IP` — один IPv4 или IPv6 адрес.

Повторы, отсутствующее значение, неправильный token, IP со списком, портом,
скобками или IPv6 zone дают неизвестный адрес. Gateway не читает браузерные
`X-Forwarded-For`, `Forwarded`, `X-PC-*`, query или JSON для определения адреса.

[Фрагмент Nginx](../config/exam-proxy.example.conf) применяется явно в существующем
HTTPS server: перенесите директивы в имеющийся `location /gateway/` либо замените
этот блок. Второй одноимённый location добавлять нельзя. Сохраните штатный regex
handoff `/gateway/.../pl/` и остальные native PL locations.
Фрагмент **перезаписывает** оба заголовка, передаёт
`$exam_verified_client_ip` и секрет из закрытого include. Private upstream Gateway
не должен быть опубликован клиентам; service token нельзя передавать по
незащищённой внешней сети. Сохранность proxy и token — часть границы доверия.

Переменная `$exam_verified_client_ip` определяется optional Deployment-фрагментом
`prairielearn-deployment/deploy/exam-client-ip.nginx.conf`: доверяется только точный
TCP peer Squid, не весь `10.0.0.0/8`. Squid должен штатно удалять присланный клиентом
XFF и выдавать единственный фактический TCP source (`forwarded_for truncate`,
`follow_x_forwarded_for deny all`). Nginx принимает RealIP только от этого peer.
Если доверенный Squid не дал пригодный адрес, переменная пуста: IP самого Squid
не приписывается студенту. Прямой клиент сохраняет свой TCP source, а его XFF
не повышает доверие. Подключение фрагментов, фактический адрес peer, Host/SNI,
режим TLS и работоспособность цепочки проверяет владелец Deployment.
Текущий стенд не считается настроенным от одного наличия этих примеров.

## Когда создаётся событие и работает ограничение

Проверка выполняется после полного `LaunchService.verify`: подпись RSA,
issuer/clientId/deploymentId, context/resource/target, state/nonce, browser
credential, сроки, роль и одноразовость уже проверены. Наблюдаются только
`student` и выбранная подписанная activity. Teacher и обычный catalog вне
выбранного списка сохраняют прежний вход и не создают экзаменационных событий.
Невалидный LTI launch не создаёт событие аудита.

Событие `verified_launch` означает подтверждённое LTI сообщение. Оно не означает
созданную PL session, потреблённый handoff, успешный Bridge enrollment,
присутствие или одновременную работу. Стабильный UID уже строится из
`[issuer, clientId, deploymentId, sub]`; имя — изменяемый отображаемый атрибут,
оно не объединяет студентов. Отдельной второй аутентификации нет.

При `restrictLaunchToClassroom: false` любое состояние адреса сохраняет обычный
redirect; в журнале стоит `gate_decision = monitor`.
При явном `true` выбранный student launch разрешён только с доверенным адресом
в `classroomCidrs`: `allowed` или `denied` фиксируются на момент события.
Unknown/untrusted/outside дают 403 без выдачи flow redirect, без `Set-Cookie`
и без Bridge вызова. Проверка LTI может уже создать кратковременную внутреннюю
попытку, но её случайный flow не выдаётся. Повтор того же launch отклоняется;
для новой попытки нужен новый явный переход из Moodle.

**Ограничение действует только на новый выбранный LTI launch.**
Существующая PL session, `/pl/`, `/socket.io/` и прямой native PL доступ не
защищены этим hook. Более того, новый разрешённый обычный catalog launch вне
`10.0.0.0/8` может создать штатную PL cookie и затем открыть доступное экзаменационное
URL. Поэтому этот переключатель не обеспечивает общий запрет внеаудиторного
доступа к оцениванию. Ограничения самого оценивания/native PL и фактический
сквозной сценарий — отдельная задача владельца Platform/Deployment.

## Необязательная передача контроллеру ExamLab

Добавьте параметр `examBinding` к выбранному курсу с уже настроенным `examAudit`.

```json
{
  "examBinding": {
    "controllerOrigin": "http://controller:8088",
    "tokenFile": "/absolute/private/exam-lti-binding-token",
    "proofTokenFile": "/absolute/private/exam-client-cert-proof-token",
    "handoffOrigin": "https://course.example:24443"
  }
}
```

Укажите точный origin контроллера с портом. Для HTTP используйте закрытую
сеть; допустимы настроенный Docker upstream `controller`, частный IP или
loopback. Токены передачи и доказательства различаются. Каждый хранится
в отдельном обычном файле с правами `0600` и содержит 64 строчных
шестнадцатеричных символа. `handoffOrigin` задаётся при наличии
отдельного HTTPS ingress проверки сертификатов на том же имени узла и другом
порту. Код использует этот origin только для выбранного подписанного входа
студента с пригодным для контроллера отображаемым именем.

Во всех обычных ingress и их private `auth_request` очищайте входящие
`X-Exam-Client-Cert-Id` и `X-Exam-Client-Cert-Proof`. На ingress проверки
сертификатов установите оба заголовка в закрытом `auth_request` при успешной
проверке клиентского сертификата по выделенному CA. Идентификатор состоит
из SHA-256 DER сертификата CA, двоеточия и серийного номера клиента в верхнем
регистре с дополнением до целого байта. Заголовок доказательства содержит token
из `proofTokenFile`. Существующий токен private handoff аутентифицирует запрос
к Gateway. Для принятия сертификата Gateway также проверяет единственность
обоих заголовков и сравнивает token доказательства в постоянное время.

Gateway добавляет доказательство к уже существующему одноразовому состоянию
handoff. После успешного штатного зачисления Bridge он отправляет `POST`
на `/exam/internal/lti-binding` с отдельным Bearer и полями `examId`, `certId`,
`uid`, `student`. Источник `examId` — настроенная область `examAudit`.
Контроллер подтверждает приём HTTP 204. На вызов отведено две секунды.
При отсутствии доказательства, несовпадении текущей области или ошибке
контроллера продолжается штатный переход в PrairieLearn.

## Журнал и просмотр оператором

Журнал хранит UTC Unix time, `verified_launch`, exam/course/activity, UID,
подписанное отображаемое имя, доверенный адрес или NULL, состояние источника,
решение gate и два сигнала. Здесь есть персональные и псевдонимные персональные
данные. JWT, raw `sub`, cookies, token, flow, email и сетевые заголовки в журнал
не сохраняются. HTTP admin endpoint не добавляется.

`ip_multiple_students` означает, что в том же course/exam раньше наблюдался
иной UID с тем же известным IP. `student_multiple_ips` — что тот же UID раньше
наблюдался с другим известным IP. Unknown не участвует в сравнении. Сигнал
сохраняется на новом событии; предыдущая строка задним числом не меняется.
Первый UID на адресе — только наблюдение: первая ошибка выбора Moodle account
не выявляется без отдельного ожидаемого соответствия. Сигналы не доказывают
нарушение, одновременность или принадлежность адреса конкретному ПК.

Сначала проверьте состояние writer, затем читайте данные штатным `sqlite3`:

```sh
sqlite3 -readonly -header -column /absolute/private/exam-audit.sqlite '
SELECT datetime(occurred_at, "unixepoch") AS utc, exam_id, activity,
       uid, display_name, source_ip, evidence_status, gate_decision,
       ip_multiple_students, student_multiple_ips
FROM exam_launches
ORDER BY id DESC LIMIT 100;'
```

Состояния источника: `inside_classroom`, `outside_classroom`, `missing_headers`,
`duplicate_headers`, `untrusted_proxy`, `invalid_ip`. Последние четыре — NULL IP.
Решение `monitor` не означает успешный вход в PL; `denied` прямо обозначает
запрет выдачи launch redirect.

При ошибке инициализации/записи аудита, включая чужую DB и SQLite lock,
пишется только постоянное предупреждение без пользовательских данных:
`Exam audit degraded; launch policy unchanged`. SQLite busy timeout — 100 мс.
Auth DB продолжает работу; решение CIDR gate от доступности audit DB не зависит.
Чужая DB проверяется read-only до DDL, journal или chmod и не исправляется.
После ошибки остаётся `app.state.exam_monitor.degraded = True` до перезапуска;
в named app это `app.state.courses[course].state.exam_monitor.degraded`.
При недоступном token корректность writer не делает источник доверенным.

Просмотр считается **degraded**, если в журнале процесса с последнего запуска
есть это предупреждение, процесс не работает либо состояние writer неизвестно.
Один SQL запрос и отсутствие строк не доказывают исправность аудита.
Оператор проверяет предупреждения штатными логами своего supervisor и не
объявляет «событий нет» при непроверенном writer. HTTP health/админ-сервис и
отдельный controller для этого не создаются.

Доставка рассчитана на текущий однопроцессный CLI. Одновременное первое создание
DB несколькими workers не квалифицировано: проигравший startup может остаться
в degraded. При остановленном writer оператор исправляет private пути/права
или выбирает новую пустую audit DB; автоматической миграции чужих DB нет.

До включения оператор задаёт короткий срок хранения для этого экзамена,
например семь дней, и ответственного за ручное удаление. Удаление выполняется
отдельной административной командой после просмотра и согласованного срока;
пример ниже изменяет только аудит, не auth state:

```sh
sqlite3 /absolute/private/exam-audit.sqlite '
PRAGMA secure_delete=ON;
DELETE FROM exam_launches WHERE occurred_at < unixepoch("now", "-7 days");'
```

Срок согласуется локально; пример не вводит автоматическое удаление или общий
срок для организации. Удаление истории сбрасывает соответствующую базу сравнения.
Копии и права доступа оператор учитывает отдельно.

## Локальная проверка и граница готовности

```sh
.venv/bin/python -m pytest -q
.venv/bin/python -m pytest -q tests/test_exam.py -k real_nginx
```

Второй тест требует системные `nginx`, `openssl` и разрешённые loopback sockets.
Он запускает настоящий Nginx TLS/RealIP и Uvicorn Gateway, использует реальные
RSA LTI подписи и временную SQLite. Trusted TCP producer с синтетическим XFF
даёт inside адрес; прямой TCP клиент со spoof XFF и обоими private headers
сохраняет собственный outside адрес. Проверяются monitor/deny, неизвестный source
и отсутствие событий для невалидного LTI. Это не echo-сервер вместо Gateway.

В этой проверке сам Squid заменён доверенным тестовым TCP peer. Отдельная
локальная проверка Deployment 17 ноября 2026 года прошла на настоящем Squid 7.7 →
Nginx TLS → синтетическом echo upstream: native truncate оставил один фактический
адрес, поддельные XFF и X-Exam headers были заменены, default delete и неизвестный
source дали unknown. Обе TLS стороны проверяли сертификаты; несовпадающий inner
Host получил 403, последующий корректный запрос — 200. Эта проверка подтверждает
производителя адреса и описана отдельно в Deployment `deploy/exam-client-ip.md`.
Дополнительная локальная композиция той же даты прошла через настоящий Squid →
Nginx TLS → Uvicorn Gateway с действительной RSA подписью LTI и временной SQLite.
Только в loopback-проверке использовался синтетический CIDR `127.0.0.3/32`:
фактический источник `127.0.0.3` получил 303/`allowed`, а `127.0.0.4` с поддельными
заголовками внутри разрешённого диапазона — 403/`denied` без flow redirect.
Свежая неверная подпись не создала события; callback не выставлял cookies.
Этот тест не меняет операторский диапазон `10.0.0.0/8` и не подтверждает
присутствие в конкретном классе.

Локальные проверки не являются сквозной приёмкой Moodle → Squid → Gateway →
native PL на живом стенде. Установка примеров, изменение production, новые
student logins и включение gate не выполнены этим пакетом. Аппаратная привязка,
Windows Guest и mTLS исключены из текущего IP договора.
